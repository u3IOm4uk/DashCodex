# Інструкції для роботи над КОНТУРОМ

КОНТУР — локальний український Excel-аналітичний дашборд. Активний runtime: кореневий `index.html`, модулі `contour*`, локальні SheetJS/ApexCharts, шрифти, зображення та `Накопичення.xlsx`.

## Мінімальний контекст

Після завантаження `AGENTS.md`, `.agent/GENERAL.md` та цього файлу для нової сесії або суттєвої задачі прочитай тільки:

1. `docs/CURRENT_STATE.md`.
2. Код модуля, якого стосується задача.

Інші документи відкривай лише за тематикою:
- `PROJECT_SPEC` — вимоги/UX;
- `ARCHITECTURE` — runtime/модулі;
- `DATA_MODEL` — Excel/агрегація/null/дати;
- `DECISIONS` — довготривалі рішення;
- `TESTING` — перевірки;
- `TODO` — незавершене;
- `README` — запуск.

Не читай весь комплект «про всяк випадок».

## Рівень задачі

- **LOW:** текст, локальний CSS, перейменування, невелика функція без зміни контрактів.
- **NORMAL:** поведінка компонента або кілька пов’язаних файлів.
- **FULL:** архітектура, модель даних, великий рефакторинг, глобальний responsive/layout або широкий ризик регресій.

Не підвищуй рівень лише через розмір проєкту.

## Change-scoped verification

Перевірки визначаються **фактичним diff**, а не запускаються повним набором автоматично:

- docs-only → runtime/browser tests не потрібні;
- змінений first-party JS → `node --check` лише змінених JS;
- Excel/schema/data/aggregate → adapter regression;
- UI/DOM/CSS/runtime → core browser smoke;
- sticky/navigation → окремий sticky test;
- charts → chart test;
- БпС/FPV/drone-related diff → окремий BpS test;
- зміна самої test/CI інфраструктури → повний quality suite, бо змінюється механізм перевірки.

Не запускай БпС-тести, якщо зміна не зачіпає БпС/FPV/drone-код або БпС-специфічні стилі. Повна регресія потрібна лише при широкому ризику.

GitHub Actions використовує `scripts/quality-scope.cjs` як канонічний маршрутизатор автоматичних перевірок. Деталі — `docs/TESTING.md`.

## Правила економії й пріоритет

- Не проводь глобальний аудит для локальної задачі й не перечитуй незмінені файли.
- Не читай без потреби `node_modules`, build/dist/coverage, кеші, логи, minified, резервні копії та історичні ревізії.
- Для великих JSON/CSV/Excel починай зі структури або вибірки.
- Перевіряй насамперед зачеплений функціонал.
- За однакової якості обирай менше контексту, файлів та інструментальних операцій.

Пріоритет у межах проєкту: **остання пряма вказівка користувача → CRITICAL `PROJECT_SPEC` → Active `DECISIONS` → код → історичні припущення**.

Не змінюй без прямої вказівки книгу/формули/схему/CRITICAL-семантику даних; не додавай публікацію, зовнішню передачу, cloud sync чи облікові записи.

## Git/GitHub дисципліна

Ці правила доповнюють загальні Git-правила з `.agent/GENERAL.md`.

- `main` — тільки перевірений стан.
- Значущі зміни роби в окремій гілці.
- Перед редагуванням на іншому пристрої виконай `git pull`.
- Перед commit перевір diff і релевантні change-scoped tests; після commit — push.
- Не створюй ручні каталоги версій або копії файлів для історії.
- Не коміть секрети, `.env`, кеші, build-артефакти або Office temp-файли.

## Коли оновлювати документацію

Ці правила уточнюють загальні правила документації з `.agent/GENERAL.md`.

Оновлюй документ лише коли змінився його предмет. Не веди revision-by-revision історію в `CURRENT_STATE` чи `TESTING`; детальна історія — `.audit/REVISIONS.md` і Git.

## Перед завершенням

1. Звір тільки зачеплені вимоги/рішення/код/TODO.
2. Виконай мінімально достатній change-scoped рівень з `docs/TESTING.md`.
3. Стару концепцію шукай у межах зачепленого модуля; борг поза обсягом занеси в TODO.
4. Коротко повідом реально виконані перевірки й обмеження.
