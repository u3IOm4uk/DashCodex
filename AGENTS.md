# Інструкції для роботи над КОНТУРОМ

КОНТУР — локальний український Excel-аналітичний дашборд. Активний runtime: кореневий `index.html` і модулі `contour*`; Dexie ToDo та старі MVC-файли не є його runtime.

## Мінімальний контекст

На початку нової сесії або суттєвої задачі прочитай тільки:

1. `AGENTS.md`.
2. `docs/CURRENT_STATE.md`.
3. Код модуля, якого стосується задача.

Інші документи відкривай лише за потреби:

| Тема задачі | Документ |
|---|---|
| чинна вимога, UX, бізнес-правило | релевантний розділ `PROJECT_SPEC.md` |
| runtime, модулі, lifecycle, інтеграції | `ARCHITECTURE.md` |
| Excel-поля, агрегація, null, дати | `DATA_MODEL.md` |
| значуще рішення або заміна концепції | релевантний запис `DECISIONS.md` |
| перевірка зміни | потрібний рівень `TESTING.md` |
| незавершена робота | `TODO.md` |
| запуск/онбординг | `README.md` |

Не читай весь комплект «про всяк випадок». Повний аудит документації потрібен лише для крос-модульної зміни, архітектури, моделі даних або реальної колізії джерел.

## Рівень задачі

- **LOW:** текст, локальний CSS, перейменування, невелика функція без зміни контрактів — тільки зачеплений компонент.
- **NORMAL:** поведінка компонента або кілька пов’язаних файлів — релевантна вимога, код і залежні сценарії.
- **FULL:** архітектура, модель даних, великий рефакторинг, глобальний responsive/layout або широкий ризик регресій — дозволений ширший аудит.

Не підвищуй рівень лише через розмір проєкту чи кількість документації.

## Правила економії й пріоритет

- Не проводь глобальний аудит для локальної задачі й не перечитуй незмінені файли в межах сесії.
- Не читай без потреби `node_modules`, build/dist/coverage, кеші, логи, minified, резервні копії, історичні ревізії та великі дампи.
- Для великих JSON/CSV/Excel починай зі структури або вибірки.
- Перевіряй насамперед зачеплений функціонал; повна регресія — тільки за широкого ризику.
- За однакової якості обирай менше контексту, файлів та інструментальних операцій.
- Якщо опис фактичної реалізації суперечить коду, фактичний стан визначає код; чинна вимога при цьому не скасовується.

Пріоритет: **остання пряма вказівка користувача → CRITICAL `PROJECT_SPEC` → Active `DECISIONS` → код → історичні припущення**. Нова явна вимога замінює несумісну стару; «можливо» не є затвердженою вимогою.

Не змінюй без прямої вказівки книгу/формули/схему/CRITICAL-семантику даних; не додавай публікацію, зовнішню передачу, cloud sync, облікові записи чи стару Dexie-базу. Зберігай reduced motion, доступність і реальні значення.

## Коли оновлювати документацію

Оновлюй документ лише коли змінився **його предмет**:

| Документ | Оновлювати коли |
|---|---|
| `PROJECT_SPEC` | змінилась чинна вимога/UX/бізнес-правило |
| `DECISIONS` | прийняте значуще довготривале рішення або заміна концепції |
| `CURRENT_STATE` | змінився фактичний стан, ключове обмеження, фокус або актуальний статус перевірки |
| `ARCHITECTURE` | змінилися модулі, потоки, lifecycle чи технічні межі |
| `DATA_MODEL` | змінилися поля, семантика, агрегація, null або дати |
| `TESTING` | змінилась стратегія/процедура перевірки |
| `TODO` | з’явилась, змінилась або закрилась незавершена задача |
| `README` | змінився запуск, онбординг або карта документації |

Не веди revision-by-revision історію в `CURRENT_STATE` чи `TESTING`; детальна історія — `.audit/REVISIONS.md`. У `CURRENT_STATE` замінюй застарілий факт актуальним, а не дописуй хронологію. Не редагуй усі документи механічно після кожної правки.

## Перед завершенням

1. Звір тільки зачеплені вимоги/рішення/код/TODO.
2. Виконай мінімально достатній LOW/NORMAL/FULL рівень з `TESTING.md`; три viewport потрібні лише для глобального responsive/layout або іншого FULL-ризику.
3. Стару концепцію шукай у межах зачепленого модуля; борг поза обсягом занеси в TODO.
4. Для документаційної задачі не змінюй runtime. Коротко повідом реально виконані перевірки й обмеження.
