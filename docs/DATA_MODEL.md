# Дані та розрахунки

Excel-контракт централізований у `js/contour-config.js` (`WORKBOOK_SCHEMA`). `contour-data.js` використовує цю схему для validation, parse/normalization та агрегації. Зміна назв аркушів, спеціальних рядків або полів повинна починатися зі зміни/перевірки схеми, а не з розкиданих string literals у runtime.

Числові рядки не конвертуються автоматично. Формули Excel не перераховуються; використовуються збережені значення книги.

## Validation до parse

`validateWorkbook(wb, XLSX)` виконується перед побудовою нормалізованої моделі й повертає `valid`, `errors`, `warnings`, `rawSheets`.

**Критичні помилки (`errors`)** блокують імпорт. Поточні критичні правила:

- книга має містити доступні аркуші;
- має бути хоча б один заповнений аркуш **ГОЧ** або **ОВгП**;
- ГОЧ з даними має мати очікувану базову структуру та підсумковий рядок `ВСЬОГО за СО:`;
- ОВгП з даними має відповідати парній структурі колонок і містити підсумкові колонки `ВСЬОГО за СО`.
- Непорожня дата кожного рядка даних відомого аркуша має бути календарно коректною. Помилка `invalid-date` блокує всю нову книгу з назвою аркуша та номером рядка Excel; попередня прийнята книга зберігається. Порожні дати пропускаються, як і раніше.

`parse()` при critical failure кидає `WorkbookValidationError` із `validation.errors`/`validation.warnings`.

**Попередження (`warnings`)** не блокують імпорт. Відсутність окремих очікуваних полів категорій у ГОЧ, БК/FPV або персоналі фіксується як warning і показується в «Про джерело». Значення не вигадуються й не замінюються нулями.

Acceptance policy поки навмисно не розширена: книга лише з персоналом/БК без заповненого ГОЧ/ОВгП не приймається.

## Аркуші

| Аркуш | Нормалізований запис / використання |
|---|---|
| ГОЧ | date, row, group + поля з першого рядка заголовків; група в колонці B. Загальний ключ **`ВСЬОГО за СО:`** з двокрапкою |
| ОВгП | date, row, name, type, kind, groups[name]=[ВЗ,БП]; два рядки заголовків, парні числові колонки з E; загальний ключ **`ВСЬОГО за СО`** без двокрапки. Вартість виключена |
| Втрати ЗСУ | date + сімейства `*_доба`, `*_рік`, `*_всього`; добові суми окремо від останніх накопичених значень |
| Застосування БК та FPV | date + `Наші війська_БК`, `Противник_БК`, `Наші війська_FPV`, `Противник_FPV` |

Назви заголовків обрізаються й нормалізуються за пробілами. Формати дат: Excel serial, коректний Date, ISO-дата/час або DD.MM.YYYY / DD/MM/YYYY; внутрішній формат YYYY-MM-DD. День, місяць і високосний рік перевіряються календарним round-trip до прийняття моделі; `date()` повертає null для невалідного значення. Зсуви дат виконуються через UTC-полудень. Числа — тільки скінченний JS number, усе інше null. `sum([])` і сума з null → null.

## Відповідність операційних категорій

Канонічні field names зберігаються в `WORKBOOK_SCHEMA.fields`; нижче — їх семантика:

| Категорія | Поля → підписи |
|---|---|
| Обстріли | `Обстріли` |
| Ракетні удари | `Ракетні удари` → Удари; `Застосовано ракет` |
| АУ / КАБ / КАР | `АУ` → Авіаудари; `КАБ`; `КАР` |
| Штурмові дії | `Бойові зіткнення` → СОУ; `Штурмові дії` → Противник |
| Тривають зіткнення | `Тривають (бз)` → СОУ; `Тривають (шд)` → Противник |
| Позиції | `Всього втрачено позицій` → Втрачено; `Відновлено позицій` → Відновлено |
| Території | `відновлено_територій`; `втрачено_територій`. Баланс = перше − друге |
| Втрати особового складу | `Втрати_всього_ЗСУ` → СОУ; `Втрати_всього_рф` → Противник |
| БпС противника | Загальний `ВСЬОГО УДАРІВ БпЛА`; на картці FPV / інші БпС |

Території — «од. джерела», бо одиниця площі відсутня. Втрати — осіб, решта поточних категорій — од. СОУ синій, противник малиновий; відновлені позиції зелені. Об’єднані поля типів не дробити штучно.

БпС у `WORKBOOK_SCHEMA.droneTypes`: `Шахеди/Гербера/Пародія`, `Італмас`, `Ланцет`, `Молнія`, `Бандероль`, `Привіт/Куб`, `FPV-дрони`. Синтетичне поле `БпС без FPV` — строга сума перших шести, незалежно від FPV і загального поля. Частки шести типів рахуються лише всередині цієї суми. Розбіжність із загальним полем показувати, не виправляти числа автоматично.

## Угруповання та ієрархія

`ContourConfig.UNIT_HIERARCHY` у `js/contour-config.js` є єдиним джерелом істини для зв’язків **угруповання → АК → підрозділ**. Вкладеність у конфігурації визначає рівень вузла: 0 — угруповання, 1 — АК, 2+ — підрозділ. `GROUP_NAMES` формується з верхнього рівня `UNIT_HIERARCHY`.

`ContourUnits.buildCatalog()` після `parse()` лише зіставляє точні назви записів ГОЧ з цією конфігурацією. Порядок рядків Excel, шаблон `АК` та інші naming/order heuristics більше не визначають parent.

Якщо в ГОЧ з’явилась назва, якої немає в `UNIT_HIERARCHY`, вона лишається окремим `unconfigured` root. UI позначає її як невизначену, але не приписує до жодного батька. Чинний browser test перевіряє синтетичний випадок, а не повне покриття bundled-книги. Невизначені вузли доступні через «Приховані» в основній таблиці; конфігураційне дерево comparison і структура configured roots їх не включають. Це обмеження охоплення, а не дозвіл виводити parent евристично.

Знаменник часток структури — сума показаних угруповань; source total обчислюється незалежно. Пояснювального coverage-підпису немає. Смуги й круглий графік використовують однакові частки; невизначені вузли доступні через «Приховані». Це не змінює totals або `UNIT_HIERARCHY`.

Ця ієрархія **не є новою Excel-схемою** і не змінює normalized records. Вона використовується для основної таблиці, direct-child деталізації та вибору unit scope у конструкторі. Явна composite-серія кількох неперекривних вузлів створюється лише в comparison presentation layer; вона не підміняє source total або parent.

Статуси `active / hidden / archived` — локальні UI-overrides у `localStorage` (`contour.unit-status.v1`). Вони не входять до Excel, не змінюють `aggregate()` і не видаляють історію. `hidden` прибирає вузол із таблиці, `archived` приховує його за замовчуванням, але дозволяє показати через «Архів» і відкрити штатні деталі за період, де є записи.

Батьківський підсумок завжди береться з його власного рядка джерела. Дочірні значення не сумуються для відтворення батька — це критично для уникнення подвійного обліку.

## Агрегація й повнота

ГОЧ: основна аналітика тільки загального рядка з `WORKBOOK_SCHEMA.rows.opsSummary`; таблиця містить і підсумки угруповань, і підрозділи, тому її рядки не можна додавати.

ОВгП фільтрується за type; підсумки з групи `WORKBOOK_SCHEMA.rows.ovgpTotal`. Персонал: ВСЬОГО, безповоротні, санітарні, зниклі_безвісті, полон; накопичені беруться з останнього запису періоду, не підсумовуються.

`aggregate` будує календарні `days`, серії по кожному полю й totals за наявними відібраними rows. День `present`, коли хоча б одна серія не null; `complete` означає `present === days.length`. Це повнота наявності днів, не сертифікація кожної клітинки. Null конкретної складової все одно блокує її порівняння.

В агрегаторі діє внутрішній safety cap `APP_CONFIG.datePolicy.maxAggregateDays = 4001`. Якщо запитаний календарний інтервал довший, `aggregate()` повертає `truncated: true`. Це аварійна технічна межа, а не UX-ліміт ручного вибору дат.

Період N днів порівнюється з N попередніми. Відсоток = `(поточне − попереднє) / abs(попереднє) × 100`. База 0 і поточне 0 → 0%; база 0 при ненульовому поточному → відсоток недоступний. Неповний період → недоступне порівняння.

## Політика дат

`APP_CONFIG.datePolicy` є єдиним runtime-контрактом меж:

- `maxManualRangeDays = 366` — максимум **включних календарних днів** у ручному діапазоні;
- `from === to` → 1 день;
- `contextWindowDays = 30`;
- `contextBeforeDays = 14`, `contextAfterDays = 15`;
- `maxAggregateDays = 4001` — внутрішній safety cap.

`inclusiveDays()` рахує саме календарні позиції включно. `validateDateRange()` використовується UI для ручного вводу. Preset «Увесь період» не проходить через ручний UX-ліміт, але агрегатор усе одно має safety cap.

Контекст доби: початково −14/+15 днів, зміщується біля меж аркуша. Внутрішні пропуски залишаються null: 30 календарних позицій не означають 30 заповнених записів. Структура не є часовим графіком і залишається за вибраний період.

## Джерело даних

Source metadata не є частиною числової моделі, але впливає на UI provenance:

```text
{ kind: 'bundled' | 'user', name: string }
```

Автоматично завантажена сусідня книга → `bundled`; File API → `user`. Назва файлу не визначає `kind`. Тому імпортований користувачем файл `Накопичення.xlsx` не маскується під bundled/test source.
